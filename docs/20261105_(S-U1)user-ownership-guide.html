CT-Chat-Router · S-U1

資料綁定使用者

登入只回答「你是誰」。這份教學說明怎麼再回答「這筆資料是不是你的」。

1先看結論

  • 每則訊息、每條分支都記錄 user_id。
  • 除了 / 和 /auth/*，所有 API 都要登入，而且只能存取自己的資料。
  • 舊資料不自動認領：你登入後，由管理腳本指定歸屬。
  • 要先修 B10，否則正式環境應該根本登入不了。
  • S-U1 完成後仍保留 Cloudflare Access，等 S-U2（每日額度）完成再討論移除。

2認證和授權是兩件事

認證（Authentication）授權（Authorization）
問題你是誰？你能動這筆資料嗎？
本專案get_current_user 讀 cookie、查 AuthSession比對資料的 user_id 和目前使用者
失敗時401404（見第 4 節）

只做認證還不夠。如果每支 API 都要求登入，卻不比對擁有者，任何登入者換一個網址裡的 id 就能讀別人的對話。這類漏洞叫 IDOR（不安全的直接物件參考）。

現況：連認證都沒有

# 任何人都能拿到所有人的訊息
curl https://fluentbranch.com/api/messages

現在擋住陌生人的只有 Cloudflare Access。程式本身的防線要由 S-U1 建立。

3B10：兩個功能搶同一個 cookie

Starlette 的 SessionMiddleware 預設使用名為 session 的 cookie，authlib 用它暫存 OAuth 的 state。登入 token 也叫 session。callback 的回應因此變成：

Set-Cookie: session=RAW_LOGIN_TOKEN; HttpOnly; Max-Age=2592000; Path=/; SameSite=lax
Set-Cookie: session=null; path=/; expires=Thu, 01 Jan 1970 00:00:00 GMT; httponly; samesite=lax

第一行由 callback 設定 token。接著 authlib 清掉 state，暫存內容變空，middleware 就在最後補上第二行，把同名 cookie 刪掉。

修法是讓兩者用不同名字，並縮短 state 的存活時間：

app.add_middleware(
    SessionMiddleware,
    secret_key=os.getenv("SESSION_SECRET_KEY", "dev-secret-change-me"),
    session_cookie="oauth_state",   # 不再和登入 token 同名
    max_age=600,                    # state 只需要活過登入流程
    same_site="lax",
    https_only=cookie_secure(),
)
測試陷阱：Python 的 cookie jar 處理這兩行的順序和 curl 不同。同一支路由用 TestClient 測，token 還在；用 curl 測，cookie 是空的。所以 harness 必須用 curl 的 cookie 檔重播登入流程，並直接檢查 Set-Cookie 標頭。真實瀏覽器要在部署後確認。

4擁有者檢查怎麼寫

把檢查集中在兩個小函式，每支路由都用它們取資料：

def get_owned_message(session, message_id, user) -> Message:
    msg = session.get(Message, message_id)
    if msg is None or msg.user_id != user.id:
        raise HTTPException(status_code=404, detail="not found")
    return msg

為什麼回 404，不回 403

403 等於告訴對方「這個 id 存在，只是不是你的」。不存在和不屬於你都回 404，對方就無法探測 id。

「預設拒絕」：NULL 也看不到

None != user.id 成立，所以還沒認領的舊資料對所有人都是 404。忘了認領只會暫時看不到，不會外洩。

三個容易漏掉的地方

① 請求內容裡的 id。檢查不能只看網址：

# POST /chat：parent_id 是使用者傳來的
{ "message": "把上面的內容重複一次", "parent_id": "<別人的訊息 id>" }

後端會沿著 parent_id 往上收集歷史送給模型，所以不檢查就等於把別人的對話念給攻擊者聽。parent_id、branch_id、anchor_message_id 都要在寫入前驗證。

② 串流緩衝。GENERATIONS 只記 id 和文字，不知道是誰的。現在的程式先查緩衝，要改成先查資料庫：

msg = get_owned_message(session, message_uuid, user)  # 先確認擁有者
if message_id in GENERATIONS:
    return StreamingResponse(_read_buffer(message_id, offset), ...)

③ 新增路由時忘了加。harness 會列舉 app.routes，未登入呼叫每一條，除了白名單都必須是 401。之後新增路由忘了保護，測試就會失敗。

5Cookie 怎麼送到後端

fetch 預設只在同源時帶 cookie。同源要協定、網域、埠都相同：

環境前端API同源？
正式fluentbranch.comfluentbranch.com/api是
本機localhost:5173localhost:8000否（埠不同）

所以前端 14 處 fetch 統一改走一個小函式，也順便集中處理登入過期：

export async function apiFetch(path, options = {}) {
  const res = await fetch(`${API_URL}${path}`, { ...options, credentials: 'include' });
  if (res.status === 401) window.dispatchEvent(new Event('auth:unauthorized'));
  return res;
}

SameSite=Lax 擋住什麼

別的網站偷偷發 POST 到我們的 API 時，瀏覽器不會帶上 Lax cookie，所以寫入型 API 受到保護。但從別站點連結導向的 GET 仍會帶 cookie，因此不能讓 GET 改變狀態。GET /auth/logout 要改成 POST。

6舊資料：先放寬、再收緊

一個 migration 無法直接加上 NOT NULL：舊資料還沒有擁有者，而擁有者要登入後才會產生。所以分兩次：

加欄位

→
部署
→
你登入
產生 User
→

→
改 NOT NULL

這個手法叫 expand / contract（擴張／收縮）。過程中資料都還在，隨時能停下來檢查。

為什麼不在登入時自動認領

最省事的做法是讓前端送出瀏覽器裡的 session_id，後端把資料歸給登入者。但 session_id 不是密碼，它曾出現在網址參數（/chats/roots?session_id=...），可能留在日誌裡。拿到它的人就能冒領資料，所以改由管理腳本處理。

# 預設只試算，不寫入
python claim_legacy_data.py --provider google --email you@example.com --session-id sess_xxx
# 確認數字後才寫入
python claim_legacy_data.py --provider google --email you@example.com --session-id sess_xxx --apply

分支怎麼認領

分支沒有 session_id。腳本依序看錨點訊息、首則訊息、attach_root_id 那則訊息的擁有者。都查不到的幽靈分支沒有任何人能使用，會被刪除。

還沒定案：認領後剩下的資料要全歸你，還是刪除，要看正式環境的查詢結果。在這之前不能執行最後的 NOT NULL 步驟。

7前端的登入閘門

現在 App 一掛載就開始抓對話。改成外面包一層 AuthGate，確認登入後才掛載 App：

function AuthGate() {
  const [user, setUser] = useState(undefined);  // undefined = 確認中，null = 未登入

  useEffect(() => {
    apiFetch('/auth/me')
      .then(r => (r.ok ? r.json() : null))
      .then(setUser)
      .catch(() => setUser(null));
    const onUnauthorized = () => setUser(null);
    window.addEventListener('auth:unauthorized', onUnauthorized);
    return () => window.removeEventListener('auth:unauthorized', onUnauthorized);
  }, []);

  if (user === undefined) return null;
  if (user === null) return <LoginPage />;
  return <App user={user} />;
}

未登入時 App 根本不存在，不會有多餘的請求。登入過期時 App 被卸載，畫面上的對話也一起消失。

登入按鈕是一般連結（<a href="/api/auth/google/login">），不是 fetch，因為整個頁面都要導向 Google。登出則是 POST 成功後重新載入頁面，確保記憶體裡沒有前一位使用者的資料。
