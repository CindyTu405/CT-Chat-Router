樂觀更新與串流 id 回傳：為什麼新對話不能開分支

看懂「樂觀更新」造成的 id 斷層，以及為什麼 id 要放在 HTTP header 回傳。

1問題現象

開一個全新的對話，送出第一則訊息，等 AI 回完之後，選取 AI 的文字想開分支——結果跳出「請先重新載入對話再建立分支」。重新整理網頁後再試，就正常了。

直覺上會想：「我不是已經送出訊息了嗎？為什麼還要重新載入？」這份文件就是解釋背後的原因，以及正確的修法。

2什麼是「樂觀更新」

當你按下送出，前端其實做了兩件事，順序是反過來的：

  1. 先樂觀地把訊息畫上去（不等後端），讓使用者覺得「秒回」。
  2. 再呼叫後端，後端把訊息寫進資料庫，回傳真正的 id。

「樂觀」的意思就是：前端先假設會成功，先把畫面做出來，之後再跟後端對答案、校正。

// 前端 handleSend：先自己畫兩則訊息，id 還沒生出來
setMessages(prev => [
  ...prev,
  { role: 'user', content: userMessageContent },      // 沒有 id
  { role: 'assistant', content: '', model_used: model } // 沒有 id（顯示 Thinking）
]);

注意看：這兩則訊息都沒有 id。因為 id 是資料庫產生的（UUID），前端在訊息真正寫進資料庫之前，根本不知道 id 是多少。

直覺：id 是「後端／資料庫」發的號碼牌，不是前端自己能決定的。樂觀更新時前端只是先把「還沒領到號碼牌」的訊息畫上去。

3id 是怎麼回傳的？—— 放在 HTTP header

後端 /chat 會把訊息寫進資料庫，此時 user 和 AI 兩則訊息都拿到了真正的 UUID。但問題來了：回應的 body 是一串正在持續產生的文字（SSE 串流），AI 的回覆是一點一點流出來的，body 裡放不下「這則訊息的 id」。

所以 id 改放在 HTTP response header（回應的檔頭）。後端目前是這樣回傳的：

# backend/main.py 的 /chat 端點
headers = {
    "X-Message-Id": ai_id,          # 只有 AI 訊息的 id
    "X-Accel-Buffering": "no",
    "Cache-Control": "no-cache",
    "Connection": "keep-alive",
}
return StreamingResponse(stream_generator(), headers=headers)

前端在「開始讀 body 之前」就能先讀 header，拿到 AI 訊息的 id：

const response = await fetch(url, ...);
const newMsgId = response.headers.get("X-Message-Id");  // AI 的 id
為什麼不塞進 body？因為 body 是「會慢慢流出來」的內容，而 id 在回應一開始就得知道（拿來做 resume、定位訊息）。header 在 body 之前就到，所以放 header 最合適。

4根因：user 訊息的 id 被漏掉了

後端只回傳了 AI 的 id（X-Message-Id），前端拿到後也只補了 AI 訊息：

lastMsg.id = newMsgId;  // 只補了最後一則（AI）的 id

結果：

訊息樂觀畫上時後端回傳後
user 訊息（messages[0]）無 id還是無 id ← 問題
AI 訊息（最後一則）無 id有 id（X-Message-Id）

開分支時，前端要拿 messages[0].id 當「這棵對話的根」（root id）：

const rootId = messages[0]?.id;
if (!rootId) {
  alert("請先重新載入對話再建立分支");  // ← 就是這個 alert
  return;
}

新對話的 messages[0] 就是那則「一直沒有 id」的樂觀 user 訊息，所以 rootId 是空的 → 彈出警語。

「重新載入」之所以能解，是因為它重新呼叫 fetchHistory，這次 messages[0] 是從資料庫抓回來的，才有真正的 id。

5修法：把 user 的 id 也回傳

既然 AI 的 id 能透過 header 回傳，user 的 id 一樣可以。作法分後端、前端兩小步：

後端：多回傳一個 header

# /chat 端點，user 訊息建立後（user_msg.id 可用）
headers = {
    "X-Message-Id": ai_id,
    "X-User-Message-Id": user_id,   # ★ 新增：user 訊息的 id
    ...
}

還有一個容易被忽略的點：瀏覽器對「跨來源（CORS）回應」的 header 有管制，預設只放行一部分。自訂的 X-User-Message-Id 必須加進 CORS 的 expose_headers，前端才讀得到：

app.add_middleware(
    CORSMiddleware,
    ...
    expose_headers=["X-Message-Id", "X-User-Message-Id"],  # ★ 加上去
)
常見坑：不加 expose_headers，前端 response.headers.get(...) 會回 null，看起來像後端沒回傳，其實是被瀏覽器擋掉了。

前端：讀到後補上第一則的 id

const newUserMsgId = response.headers.get("X-User-Message-Id");
if (newUserMsgId) {
  setMessages(prev => {
    // 只補「畫面第一則、是 user、而且還沒有 id」的那則
    const first = prev[0];
    if (!first || first.role !== 'user' || first.id) return prev;
    const next = [...prev];
    next[0] = { ...first, id: newUserMsgId };
    return next;
  });
}

補上之後，messages[0].id 在送出後立刻就有值，不用等重新載入，開分支就能正常拿到 root id。

6動手前的練習

  1. 「樂觀更新」的「樂觀」是指什麼？為什麼前端畫上的訊息一開始沒有 id？
  2. 為什麼 id 要放在 response header，而不是 SSE 的 body 裡？
  3. 為什麼加了 X-User-Message-Id header 後，還一定要加進 expose_headers？
  4. 前端補 messages[0].id 時，為什麼要檢查「是 user 而且還沒有 id」？（想想：如果不是新對話，會發生什麼事？）

實作範圍：後端 /chat 加 header＋expose_headers；前端 handleSend 讀 header 補 id。確認概念 OK 後由子代理實作（commit 編號 G1）。
