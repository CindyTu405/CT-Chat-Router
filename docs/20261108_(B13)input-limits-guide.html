輸入長度上限與限流

任何登入者都能一直寫入大量資料、塞滿磁碟。這份教學說明怎麼用「欄位上限」和「限流」把它擋住。

1問題

目前後端收到的文字欄位都沒有長度限制，唯一的關卡是 nginx 預設的請求大小上限 1 MB。所以：

  • /chat 一則訊息可以接近 1 MB。生成失敗會退回額度，所以每日 20 次也擋不住寫入。
  • 建立分支、改標題、relink 這三個端點完全沒有限流，可以用程式一秒打好幾次，每次寫進接近 1 MB 的 anchor_text。
為什麼重要：EC2 的磁碟（EBS）有固定大小。寫滿之後 PostgreSQL 停止寫入，整站無法使用，連正常用戶也受影響。只要一個帳號就能做到。

2概念：輸入驗證

FastAPI 用 Pydantic 模型檢查請求內容。欄位加上 max_length 之後，太長的請求在進到端點程式之前就被擋下，自動回 422，不會碰到資料庫，也不會扣額度。

max_length 算的是「字元數」，中文一個字算 1，英文一個字母也算 1。

前端也要擋，但不能只靠前端：前端的檢查是為了讓正常用戶早點看到提示；攻擊者可以直接呼叫 API 跳過前端，所以後端的檢查才是真正的防線。

3概念：限流

限流就是「每人每段時間最多幾次」。/chat 和重新生成已經用 slowapi 限制每人每分鐘 10 次（V1-2）。這次把同一套套用到其他會寫入資料的端點，key 一樣用登入 cookie 的雜湊，同一個網路下的不同用戶互不影響。

上限 + 限流合起來，就能算出一個人最多寫得進多少資料：每分鐘 30 次 × 5,000 字，大約是 /chat 一次的上限量級，而不是無限。

前端的處理：

  • 送訊息、編輯最後一則：超過 20,000 字跳提示，不送出，輸入內容保留。
  • 改標題：輸入框加 maxLength={200}，打不進第 201 個字。
  • 建立分支、relink：anchor_text 只是標題和顯示用的快照，送出前截到 5,000 字。高亮位置用的是 offset，不受影響。
  • 這三個端點被限流（429）：跳提示「操作太頻繁，請稍後再試」。

5怎麼驗收

  • harness：20,000 字的訊息成功，20,001 字回 422，DB 沒有新增訊息，額度沒有被扣。
  • harness：標題 201 字、anchor_text 5,001 字都回 422。
  • harness：同一人一分鐘內建立分支第 31 次回 429；另一個用戶同時不受影響。
  • 既有 harness 全部 ALL PASS。
  • 瀏覽器：貼一段超過 20,000 字的文字送出，看到提示且輸入框還在；改標題打不進第 201 個字；正常聊天、建立分支不受影響。
