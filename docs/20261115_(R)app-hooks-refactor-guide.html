拆分 App.jsx：自訂 Hook

App.jsx 有 1,139 行，送訊息、串流、分支、額度、模型選單全在一個元件裡。這份教學說明怎麼用自訂 Hook 把它拆開，以及為什麼要一小步一小步做。

1現況與問題

數字意思
1,139 行一個檔案裡塞了六種不同的工作
約 30 個 useState任何一個改變都可能牽動其他地方
5 個幾乎一樣的「讀串流」迴圈送訊息、重新生成、分支送訊息、分支重新生成、續讀。修一個 bug 要記得改五個地方

症狀：之後每加一個前端功能（例如時間軸 T1、幽靈分支 E5），都要在這 1,139 行裡找位置，而且很難確定沒有影響到別的功能。

2概念：自訂 Hook

Hook 就是 useState、useEffect 這些以 use 開頭的函式。自訂 Hook 是你自己寫的、以 use 開頭、裡面再呼叫其他 Hook 的函式。它讓你把「一組相關的狀態加上操作它們的程式」搬到另一個檔案。

// 示意，實際程式由 implementer 撰寫
// 拆之前：全部寫在 App 裡
function App() {
  const [presets, setPresets] = useState([]);
  const [defaultModel, setDefaultModel] = useState(null);
  useEffect(() => { apiFetch('/api/model-options').then(...) }, [openrouterConnected]);
  ...
}

// 拆之後：搬到 useModelOptions.js
export function useModelOptions(openrouterConnected) {
  const [presets, setPresets] = useState([]);
  const [defaultModel, setDefaultModel] = useState(null);
  useEffect(() => { ... }, [openrouterConnected]);
  return { presets, defaultModel, ... };       // 把外面需要的東西交出去
}

function App() {
  const { presets, defaultModel, ... } = useModelOptions(openrouterConnected);
  ...
}
常見誤解實際情況
拆出去之後狀態就「共用」了不會。每個呼叫 Hook 的元件各自有一份狀態，和寫在元件裡完全一樣
Hook 是一種元件不是。它不畫畫面，只回傳資料與函式；畫面仍由 App 與子元件負責
拆了會變慢不會。React 執行起來和原本寫在 App 裡是一樣的
Hook 的規則照舊：只能在元件或其他 Hook 的最上層呼叫，不能放在 if 或迴圈裡。

3概念：重構的紀律

重構是「改寫程式的結構，但使用者看到的行為完全不變」。業界做法有三條：

  1. 先有測試。上一步做的六條 E2E 測試就是為了這個：每拆一步就跑一次，馬上知道有沒有弄壞。
  2. 一次只做一件事。一個 commit 只搬一塊，不順便修 bug、不順便改功能。出問題時只要退回一個 commit。
  3. 搬移和改寫分開。「把程式原封不動搬到另一個檔案」風險很低；「把五份很像的程式合成一份」是改寫，風險高。兩種不放在同一步。
拆的時候發現 bug 怎麼辦？記進 BUGS.md，照原樣搬過去，之後另開一步修。重構那一步只負責「行為不變」。

4要拆成哪幾塊

新檔案內容種類風險
quotaErrors.js額度錯誤的判斷與文字、輸入長度上限搬移（純函式，沒有 React）低
hooks/useModelOptions.js模型清單、預設模型、自訂模型開關搬移低
readTextStream.js五個讀串流迴圈合成一個函式改寫高
hooks/useBranchPanel.js分支面板的狀態、開分支、分支送訊息與重新生成搬移中
hooks/useMainChat.js主對話的訊息、送出、重新生成、載入、續讀搬移中高（和分支互相呼叫）

側欄（改名、刪除、排序）與樹狀圖視窗比較單純，這一輪先留在 App.jsx。預估拆完 App.jsx 剩約 300–400 行，主要是把各個 Hook 接起來、交給子元件。

5最難的一步：合併五個讀串流迴圈

五個迴圈的骨架一樣，差在三個地方：

差異主對話（送出、重新生成、續讀）分支（送出、重新生成）
切到別的對話時停止有（讀之前、讀之後各檢查一次）沒有（寫回指定的分支，不受切換影響）
文字寫到哪裡最後一則，或指定 id 的那則指定分支裡的最後一則或指定 id 的那則
需要知道「有沒有完整讀完」重新生成需要（讀完才重抓分支高亮）不需要

所以共用函式只負責「讀」，差異由呼叫的人傳進來：

// 示意，實際程式由 implementer 撰寫
const { finished } = await readTextStream(response, {
  shouldStop: () => activeRootIdRef.current !== convId,   // 分支不傳 → 永不停止
  onText: (text) => setMessages(prev => 寫進對的那一則),  // 每收到一段就呼叫，text 是目前累積的全文
});
為什麼這步前要先補測試：現有六條 E2E 涵蓋主對話送出、重新生成、分支送出、切換對話，但沒有涵蓋分支重新生成和編輯最後一則訊息。這兩條路徑也會改到，所以先各補一條測試。

6順便處理：讓測試更穩

上一輪的測試有兩個定位方式比較脆弱：

  • 送出按鈕沒有文字也沒有 aria-label，測試只能找「輸入框後面的第一個按鈕」。
  • 主對話訊息區靠 CSS class 找，哪天改樣式測試就壞。

提議在第一步加 aria-label="送出"（螢幕閱讀器使用者也受益）與 data-testid="message-list"（對使用者沒有任何影響），再把測試改用它們。這是拆分前唯一會改到產品畫面元素的地方，畫面看起來不變。

7怎麼驗收

  • 每一步：npm run build 成功、npm run test:e2e 全部通過、只改到該步列出的檔案。
  • 每一步：App.jsx 行數比上一步少（補測試那步除外）。
  • 全部做完後：你在瀏覽器照一份清單走一次（桌面與手機寬度），因為 E2E 沒有涵蓋手機版、選字建立分支、登入與 OpenRouter 連結。

完整的可執行指令在 PLAN_v2.md「R 規格與驗收」。
