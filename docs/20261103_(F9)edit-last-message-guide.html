編輯最後一則 user 訊息

沿用重新生成端點加一個可選欄位、檢查都在寫入之前、編輯狀態放在共用元件、從資料推導警語、樂觀更新與還原。

1要做成什麼樣子

  • 最後一則 user 訊息可以編輯：桌面在送出時間右邊的功能列（複製右邊）多一支鉛筆（lucide Pencil）；手機長按選單多一項「編輯」。
  • 點了之後，user 泡泡原地變成編輯框（不回到底部輸入框）。
  • 送出 → user 訊息內容換成新的，下面那則 AI 回覆用選單目前的模型重新生成。兩則訊息的 id 都不變，不刪任何訊息。
  • 那則 AI 回覆上如果有分支：編輯框下方紅色小字「此回覆上有 N 個分支，重新生成後會變成幽靈分支」；送出後這些分支幽靈化（同 G6）。
  • 主對話與分支面板共用同一套元件，分支面板最後一則 user 也能編輯。
  • 在 branch feat/f9-edit-last-message 開發，F9-1、F9-2 都驗收後 merge 回 main。

2概念一：同一個端點，多一個「可選」欄位

原本 DESIGN_P3 主題 3 打算開新端點 /messages/{id}/edit，先刪舊一輪再建新的。G6 已經做好「原地重新生成」，編輯只比它多一件事：先改 user 內容。所以直接擴充 G6 的端點：

# backend/models.py
class RegenerateRequest(SQLModel):
    model: str
    content: Optional[str] = None     # F9：有帶 = 編輯；沒帶 = 純重傳（G6 原行為）
另開 /edit 端點regenerate 加可選欄位（採用）
重複程式404／403／409 檢查、幽靈化、背景生成、串流全部要再寫一份或抽函式只多幾行
舊前端不受影響也不受影響：不帶 content 的請求行為完全不變
前端呼叫新的 fetch 流程G6-2 的 handleRetry 多傳一個參數

「加可選欄位、預設值等於舊行為」是 API 演進的常用手法，叫向後相容（backward compatible）：舊的呼叫方不用改。

端點裡新增的部分：

if payload.content is not None and not payload.content.strip():
    raise HTTPException(422, "content is empty")       # 404 之後、任何寫入之前
...（403、409、409 檢查，同 G6）...
if payload.content is not None:
    user_msg.content = payload.content                 # ← 新增
    session.add(user_msg)
user_content = user_msg.content                        # 生成用新內容
...幽靈化、ai.content = ""、換模型...
session.commit()                                       # 全部一起

3概念二：檢查都在寫入之前（原子性）

一次編輯要改三樣東西：user 內容、AI 內容與模型、分支幽靈化。這三樣必須同一個 commit：

如果分開 commit會發生什麼
先改 user、再檢查 409 失敗user 已經是新內容，但 AI 還是回答舊問題 → 一問一答對不上
改了 user＋AI，幽靈化前程式出錯分支高亮還錨在已經不存在的文字位置上

做法跟 G6 一樣：所有會拒絕的檢查放在最前面，任何一個失敗就直接回錯誤，資料庫完全沒動；全部通過才開始改，最後一次 commit()。

順序情況回應
1id 不存在或不是 AI404
2帶了 content 但全是空白422（新增）
3模型不在白名單403
4還在生成中409
5不是最後一則409
全部通過 → 改 user、幽靈化、清空 AI → 一次 commit200 串流

422 Unprocessable Entity：「格式對，但內容不能用」。FastAPI 本身驗證 body 失敗也是回 422，語意一致。

測試怎麼證明：harness 對一則「不是最後一則」的 AI 帶 content 送出 → 期待 409，然後讀資料庫，user 內容必須還是舊的。這就證明檢查在寫入之前。

4概念三：編輯狀態放在共用元件裡

G3 之後主對話與分支面板用同一個 MessageList。編輯功能放在這裡，兩邊就同時有：

// MessageList.jsx（概念）
const [editingId, setEditingId] = useState(null);   // 正在編輯哪一則 user 訊息

// 這則能不能編輯：由資料「算出來」，不另存 state
const canEdit = (msg, index) =>
  onEdit && !isLoading &&
  msg.role === 'user' && msg.id &&
  index === messages.length - 2 &&
  messages[index + 1]?.role === 'assistant' && messages[index + 1]?.id;
誰管什麼內容
MessageList哪一則在編輯（editingId）、能不能編輯、把 user 泡泡換成編輯框
UserMessageEditor（新檔）textarea、自動長高、鍵盤、送出停用條件、紅色警語、取消／送出按鈕
MessageActions功能清單多一項「編輯」（桌面圖示列與手機長按選單共用同一張清單，G8 的設計）
App真正打 API、寫回 state（主對話與分支各一個函式，透過 onEdit prop 傳進來）

為什麼「最後一則 user」是 length - 2

對話是一問一答，最後一則是 AI 回覆，它前面那則才是最後一則 user。條件裡同時要求「下一則是 assistant 而且有 id」：前端「⚠️ 連線錯誤」那種沒有 id 的回覆，後端端點找不到它，所以不給編輯（重新整理後就有 id 了）。

什麼時候自動關閉編輯框

  • 按取消、按送出。
  • isLoading 變成 true：例如編輯到一半，從底部輸入框送出新訊息。那則就不再是最後一則了。
  • 該則不再符合 canEdit（例如切換到別的對話）。渲染時用 editingId === msg.id && canEdit(msg, index) 判斷，不用另外清 state 也不會顯示錯的編輯框。

5概念四：編輯框的細節

外觀

  • user 欄位平常是 items-end max-w-[85%] md:max-w-[75%]（泡泡跟著文字長短縮放）。編輯中加 w-full，撐到同一個上限，短訊息也有足夠空間改。
  • 自動長高：跟 ChatInput 一樣，先把高度設 auto 再設成 scrollHeight；上限 10 行（對齊 G9 摺疊行數），超過在框內捲動。
  • 開啟時自動聚焦，游標放在文字結尾（setSelectionRange(len, len)）。
  • 編輯中隱藏送出時間與功能列；不掛 G8 的長按事件，也不套 select-none（不然手機不能在框內選字）。

鍵盤

沿用 keyUtils.js 的 handleEnterKey（桌面 Enter 送出、Shift+Enter 換行；手機 Enter 換行），另外加 Esc 取消：

const onKeyDown = (e) => {
  if (e.key === 'Escape') { e.preventDefault(); onCancel(); return; }
  handleEnterKey(e, () => { if (canSubmit) onSubmit(text); });
};

送出停用

const canSubmit = text.trim() !== '' && text !== original;

沒改內容就送出等於重傳，那是 G6 重傳鈕的工作。停用可以避免誤觸又打一次付費模型。後端仍然擋空白（第 3 節的 422），前端停用只是第一道。

紅色警語：從資料推導，不另存

// branchList 是 App 已經抓好的「這串對話的分支」，G6 重傳後也會重抓
const branchCount = branchList.filter(b => b.anchor_message_id === aiMsg.id).length;

{branchCount > 0 && (
  <p className="text-xs text-red-500">此回覆上有 {branchCount} 個分支，重新生成後會變成幽靈分支</p>
)}

不用 anchorsByMessageId：那張表只收有 anchor_text 的分支（畫高亮用）。還沒送出訊息的空分支也會被幽靈化，所以要算進去。分支面板裡不能再開分支，branchList 是空的，警語自然不會出現。

6概念五：樂觀更新與還原

樂觀更新（G1 教過）：不等伺服器回應，先把畫面改成「應該會成功」的樣子。編輯送出時：

// App.jsx：擴充 G6-2 的 handleRetry，不另寫一套串流迴圈
// MessageList 呼叫 onEdit(userMsg, aiMsg, text) → App 轉成 handleRetry(aiMsg, { userMsg, content: text })
const handleRetry = async (aiMsg, { userMsg, content } = {}) => {
  const oldUser = userMsg?.content;              // 先記下舊內容，失敗時還原用
  // 1. 樂觀：user 換新內容、AI 清空
  setMessages(prev => prev.map(m =>
    content != null && m.id === userMsg.id ? { ...m, content } :
    m.id === aiMsg.id ? { ...m, content: '', model_used: model } : m));
  const res = await fetch(`.../messages/${aiMsg.id}/regenerate`,
    { body: JSON.stringify(content != null ? { model, content } : { model }) });
  if (!res.ok) {
    // 2. 被拒（409／403／422）：資料庫沒變 → user 還原舊內容；AI 顯示連線錯誤（同 G6-2）
  }
  // 3. 其餘照 G6-2：串流寫回同 id、loadBranchList、關掉幽靈分支 tab
};
失敗發生在資料庫畫面
請求被拒（4xx）或根本沒送出去沒變user 還原舊內容；AI 那則「⚠️ 連線錯誤」
串流中途斷線user 已是新內容、AI 生成到一半user 保持新內容；AI「⚠️ 連線錯誤」；可按 G6 重傳鈕
注意：還原時要用「送出前記下的舊內容」，不能從畫面的 state 讀，因為 state 已經被第 1 步改掉了。這就是 oldUser 先存起來的原因。
