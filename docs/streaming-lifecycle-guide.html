串流生命週期：為什麼切走再切回會卡住

AI 回覆是「邊產生邊傳」的。這篇解釋它為什麼會因為切換對話而中斷，以及我們打算怎麼改。目前只有設計與教學，程式碼尚未修改。

0. 現象與根因摘要

  • 現象：送出訊息後切到別的對話，再切回來，那則 AI 回覆一直顯示 Thinking...，重新整理也一樣。
  • 根因：AI 回覆的內容只在「串流全部跑完」後才寫進資料庫。切換對話時，前端把連線切斷，後端的串流也跟著停止，於是資料庫裡留下一則內容是空字串的 AI 訊息。
  • 所以：不是前端顯示有問題，而是「資料還沒存下來」。要修的是後端生成與連線的關係。

1. 串流（Streaming）是什麼？

一般的 HTTP 請求是「一問一答」：瀏覽器送出請求，伺服器整份準備好，一次回傳。AI 回覆可能要生成十幾秒，若等全部完成才回傳，使用者只會看到空白。

串流的做法是：伺服器一邊生成、一邊把小段文字送出去，瀏覽器一邊收、一邊顯示。連線在整個過程中保持開啟。

瀏覽器 POST /chat→ 後端開始生成→ chunk 1→ chunk 2→ …→ 連線結束
關鍵觀念
這條連線是「傳輸通道」，不是「生成工作」。生成的 AI 工作在後端執行，連線只負責把結果送到瀏覽器。把這兩件事分開，就是這次修法的核心。

2. 目前的程式碼：兩條斷線路徑

切換對話時，同時有兩個地方會把串流停掉：

路徑 A：前端主動中止（frontend/src/App.jsx）

loadChat 切換對話時會呼叫 streamAbortRef.current.abort()。abort() 會取消瀏覽器這一端的 fetch，連線被關閉。

路徑 B：後端收到斷線（backend/main.py）

後端的 stream_generator 是一個 Python 生成器（generator）：它一邊 yield 內容給 StreamingResponse，一邊累積到 full_response。連線斷掉時，FastAPI 會停止迭代這個生成器，後面的存檔程式碼就不會執行。

# backend/main.py（簡化）
async def stream_generator():
    full_response = ""
    async for chunk in stream:      # 連線斷掉 → 這個迴圈會被中止
        full_response += chunk
        yield chunk
    # 存檔只在迴圈「正常跑完」後才會執行
    ai_msg.content = full_response
    session.commit()
切換對話→ 前端 abort()→ 連線關閉→ 後端生成器停止→ 存檔程式碼沒執行→ DB 內容 = ""
為什麼切回也救不了
資料庫裡那則 AI 訊息的內容是空字串。切回時前端去讀 history，拿到的就是空的，所以一直顯示 Thinking...。重新整理也只是再讀一次同樣的空字串。

3. 核心概念：生產與傳輸分離

目前的設計是「一條連線 = 一次生成」，連線斷了生成就跟著結束。我們要改成：

目前改成
生成在哪執行綁在 HTTP 請求的生成器裡獨立的背景任務（asyncio task）
連線斷掉生成跟著停止生成繼續，只是沒人在收
結果存在哪生成完才寫入 DB邊生成邊寫入記憶體緩衝；完成時寫入 DB
切回對話讀 DB，拿到空字串讀緩衝，拿到目前為止的內容；若還在生成就繼續等

什麼是 asyncio task？

Python 的 asyncio.create_task(coro) 會把一個協程排進事件迴圈，讓它在背景獨立執行。它不像生成器那樣「綁在某個請求上」，請求結束或斷線都不會自動取消它（除非我們主動取消）。

task = asyncio.create_task(run_generation(ai_msg_id, ...))
# 這裡可以立刻回傳，task 會在背景繼續跑

4. 方案設計

4-1. 後端：生成任務 + 記憶體緩衝

  • 建立一個 registry（字典），key 是 AI 訊息的 id，value 是 { text, done, error }。
  • /chat 送出時建立 task：task 把每個 chunk 追加到 text；完成後設 done = True，並把最終內容寫入 DB。
  • 錯誤時也要寫入（例如內容後面附上「生成中斷」），避免 DB 留空字串又沒有說明。
  • /chat 本身仍然以串流回應，從 registry 讀取並送給瀏覽器；斷線時只結束「這次的讀取」，不取消 task。

4-2. 後端：新增一個可續讀的端點

GET /messages/{id}/stream?offset=N
→ 回傳 registry 裡從第 N 個字元開始的內容
→ 若 done = false，就一直等到有新內容或完成（或逾時）

前端記住自己已經收到幾個字元（offset），切回時從那個位置續讀，不會重複或漏掉。

4-3. 前端：切換時不 abort

  • 切換對話時不呼叫 abort()，只是停止「畫面更新」（現在已有的 activeRootIdRef 檢查就是做這件事）。
  • 切回來時，如果最後一則 AI 訊息還在生成（registry 裡 done = false），就用 offset 續讀，直到完成。
  • 如果已完成，直接讀 history 即可。

4-4. 更簡單的替代方案（若不想做串流續讀）

切回時每秒輪詢一次 GET /messages/{id}，直到 done 為止。實作量比續讀少，代價是內容更新會有 1 秒延遲，而且每秒一次請求。

5. 取捨與風險

項目說明
記憶體緩衝會遺失後端重啟時，正在生成中的內容會消失。DB 仍會保留「完成前已寫入的最後狀態」，需要決定是否定期寫入 DB。
只能單一 workerregistry 在程序記憶體中，多個 uvicorn worker 之間不共享。目前 docker-compose 是單一程序（--reload），可以接受；日後水平擴展時要改用 Redis 或資料庫。
背景任務的錯誤task 內的例外不會自動傳給請求，必須在 task 內自己捕捉並寫入 registry 與 DB。
使用者真的想停止目前取消 AbortController 等於「停止」。改成不取消後，需要另外提供「停止生成」按鈕（對應 PLAN 中被取消的 S3）。
資源消耗切走的對話仍會消耗 API 額度直到生成完成。

6. 需要你決定的問題

  • A. 切走時要不要繼續生成？（你選了「繼續」，這裡只是確認）
  • B. 續讀（4-2）還是輪詢（4-4）？續讀較即時、較複雜；輪詢簡單、有 1 秒延遲。
  • C. 「停止生成」按鈕要不要做？目前沒有這個功能，修完後需要一個明確的停止方式。
  • D. 後端重啟時正在生成的內容：接受遺失，或每 N 個 chunk 寫一次 DB？
