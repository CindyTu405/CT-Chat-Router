create_all 是什麼

它怎麼建表、為什麼以前離不開它、又為什麼現在要停用。

1一句話解釋

create_all 就是「把你 code 裡定義的資料表，缺哪張就建哪張」的內建功能。

在這個專案裡，它包在 backend/database.py：

# backend/database.py
def create_db_and_tables():
    SQLModel.metadata.create_all(engine)

然後由 FastAPI 的 lifespan（伺服器啟動時）呼叫：

# backend/main.py
@asynccontextmanager
async def lifespan(app: FastAPI):
    print("正在檢查並建立資料庫 Table...")
    create_db_and_tables()   # 啟動時自動建表
    yield

所以每次伺服器啟動，它都會「檢查一遍有沒有缺表」。

2它到底做了什麼

你的 model 檔裡，凡是 table=True 的類別，都是一張「表的定義」：

  • Message → message 表
  • User → user 表
  • AuthSession → auth_session 表
  • FreeModelsCache → freemodelscache 表

create_all 會把這些定義收集起來，對每一張「資料庫裡還不存在」的表執行 CREATE TABLE：

models.py
(所有 table=True 的定義)
→
掃描資料庫
(哪些表缺了)
→
補建缺的表
(CREATE TABLE)

關鍵字是「缺」——它只補「不存在」的表，已存在的完全不理。

3它的三個致命限制

① 只建不「改」

表已經存在，它就跳過。你想給現有表「加一個欄位」，它一點忙都幫不上。

這個專案就吃過虧：你之前要加 title、session_id 欄位時，create_all 完全無動於衷（因為 message 表早就建好了），最後只好手寫一支 migrate.py，用 ALTER TABLE 硬加：
# 舊的 backend/migrate.py（手動救火）
session.exec(text("ALTER TABLE message ADD COLUMN IF NOT EXISTS title VARCHAR;"))
session.exec(text("ALTER TABLE message ADD COLUMN IF NOT EXISTS session_id VARCHAR DEFAULT 'default';"))

② 沒有版本紀錄

它不知道「建過什麼、建到哪一版」。每次就傻傻地「缺什麼補什麼」，沒有歷史可以查。

③ 不能回退

建錯了沒有「退回上一版」的機制，只能自己手動救。

4create_all vs Alembic

能力create_allAlembic
建新表✅✅
改現有表（加欄位、改型別）❌ 不會動✅ autogenerate 自動產生
版本紀錄（知道建到哪）❌✅ alembic_version 表
回退上一版❌✅ downgrade
多台環境同步❌ 容易不同步✅ 每台各自 upgrade head

結論：create_all 適合「第一次把整個資料庫建出來」的雛形階段；專案長大、要改結構之後，就該換 Alembic。

5為什麼現在要停用它

我們已經引了 Alembic（見 Alembic 教學）。如果兩者並存，等於兩套系統同時在管資料庫結構，會打架：

  • Alembic 的紀錄說「我建到 v3」，但 create_all 又默默建了一張 Alembic 不知道的表。
  • 之後 alembic revision --autogenerate 比對時就會看到「憑空多出來的表」，產生錯亂。
所以 P0-10 要做的，就是把 lifespan 裡那行 create_db_and_tables() 拿掉。以後建表、改表一律走 Alembic。

6停用之後，建表靠什麼

靠一條指令：

alembic upgrade head   # 套用所有 migration，建出/更新到最新結構

以後的標準流程變成：

改 model
(加表/加欄位)
→
revision --autogenerate
(產生 migration)
→
檢查 migration
→
upgrade head
(套用)

乾淨、可重現、可回退，而且每台機器（本機、Render 正式機）都長得一樣。
