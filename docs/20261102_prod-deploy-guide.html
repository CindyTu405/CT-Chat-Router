正式環境怎麼更新

compose 檔怎麼選、volume 掛載是什麼、pull 之後該下哪些指令。

1為什麼會出事（2026-11-02 的事故）

在 VM 上 git pull 之後 docker compose up，網頁送訊息回 500：

psycopg2.errors.UndefinedColumn: column "branch_id" of relation "message" does not exist

原因：程式碼更新了，資料庫的結構沒跟上。新版 Message model 有 branch_id，但 VM 的 Postgres 資料還是舊的（volume 保留了資料，log 才會寫 "Skipping initialization"）。git pull 與 docker compose up 都不會去執行 Alembic migration，要自己跑。

git pull
(程式碼是新的)
→
DB 沒動
(結構還是舊的)
→
INSERT 找不到欄位
(500)

2兩份 compose 檔：開發 vs 正式

docker-compose.yml（本機開發）docker-compose.prod.yml（VM）
api 啟動指令uvicorn ... --reloaduvicorn ...（無 reload）
api 掛載原始碼有（./backend:/app）沒有
對外 portdb 5432、api 8000、pgadmin 5050只開 web 的 80；db、api 只在 compose 內部網路
pgadmin有沒有
restart—restart: always（機器重開會自動起來）

為什麼 VM 上直接打 docker compose ... 就是 prod？

VM 的 .env 裡有這一行：

COMPOSE_FILE=docker-compose.prod.yml

COMPOSE_FILE 是 Docker Compose 自己讀的環境變數，作用等同每次都加 -f docker-compose.prod.yml。沒有它，Compose 會預設讀 docker-compose.yml（開發版）。

如何確認現在用哪一份：sudo docker compose config --services 看服務清單；prod 沒有 pgadmin。

3volume 掛載是什麼

容器的檔案系統是「用完即丟」的：容器刪掉重建，裡面的東西就沒了。volume 掛載就是把容器外面的某個東西接進容器裡，讓兩邊看到同一份內容。這個專案用到兩種：

① Bind mount（綁定目錄）：./backend:/app

格式 主機路徑:容器路徑。把主機上的 ./backend 資料夾直接蓋在容器的 /app 上。

主機 ./backend
(你改 main.py)
⇄
容器 /app
(馬上看到新的)

搭配 --reload，存檔後 uvicorn 立刻重啟，這就是開發時「改了就生效」的原因。只有開發版 compose 有這行。

② Named volume（具名 volume）：postgres_data:/var/lib/postgresql/data

冒號左邊不是路徑而是名字，資料存在 Docker 自己管理的位置。把資料庫檔案放在這裡，容器刪掉重建，資料還在。開發與正式版都有。

兩種掛載對部署的影響

情況開發版正式版
程式碼從哪來主機資料夾（bind mount）build 時 COPY 進 image 的那一份
git pull 後容器自動看到新碼容器還是舊碼，要重新 build
資料庫資料都在 postgres_data：重建容器不會清掉，所以舊 schema 會一直留著，必須用 migration 改
危險指令：docker compose down -v 的 -v 會連 named volume 一起刪，等於清空資料庫。正式環境不要加 -v。

4每次部署的標準流程

# 在 VM 的專案目錄
git pull
sudo docker compose up -d --build
sudo docker compose exec api alembic upgrade head
sudo docker compose logs -f api
指令意思
git pull把 GitHub 上最新程式碼拉到 VM 的資料夾。只動檔案，不影響正在跑的容器。
sudo以管理員身分執行。VM 上目前使用者沒加進 docker 群組，所以 docker 指令都要 sudo。
docker compose up依 compose 檔建立並啟動所有服務。已在跑且設定沒變的容器不會被動到。
-ddetached，背景執行。不加的話終端機會被 log 佔住，Ctrl+C 就把服務停了。
--build啟動前先重新 build image。prod 的程式碼在 image 裡，pull 後一定要加，否則跑的還是舊碼。
docker compose exec api ...在已經在跑的 api 容器裡執行指令（api 是 compose 的服務名）。對比 run：run 會另開一個新容器。
alembic upgrade head讀 DB 的 alembic_version 表，把還沒套用的 migration 依序執行到最新版（head）。已是最新就什麼也不做，可以重複執行。
alembic current只看 DB 目前在哪一版，不改任何東西。
docker compose logs -f api看 api 的 log。-f follow，持續輸出；Ctrl+C 離開，不會停掉服務。
docker compose ps列出各容器狀態（Up / Exited / healthy）。
docker compose down停止並移除容器與網路。不加 -v 就不會刪資料。
順序有道理：先 --build 讓新碼上線，再 migration。新碼若在 migration 前被呼叫會 500，所以兩步之間盡量別拖；沒有新 migration 檔就可以跳過第三步。

5驗證資料庫欄位

sudo docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\d message"'

為什麼要包一層 sh -c '...'、還要單引號？

  • $POSTGRES_USER 是 db 容器的環境變數，由 compose 傳進去。
  • 如果直接寫 ... psql -U $POSTGRES_USER ...，變數會先被 VM 的 shell 展開；VM 沒設這個變數，結果變空字串，psql 就把 -d 當成使用者名稱，才會看到 role "-d" does not exist。
  • 單引號讓外層 shell 不展開，留給容器內的 sh 展開。

\d message 是 psql 的內建指令，列出 message 表的欄位，應看到 branch_id、anchor_message_id。

7小練習

  1. 在 VM 跑 sudo docker compose config --services，確認沒有 pgadmin。
  2. 跑 alembic current，確認輸出是 b1a2c3d4e5f6 (head)。
  3. 用 docker compose ps 與 docker volume ls 各找出三個容器與 postgres_data。
  4. 說說看：如果在 prod 只 git pull 再 docker compose restart api，程式碼會更新嗎？（不會，為什麼？）
