分支入口、重疊降級、分支列表與幽靈重連

用「有沒有 offset」區分高亮與底部入口、半開區間的重疊判定、一個交易改兩筆資料、重連時把分支接回新位置、面板內的滿版覆蓋與捲到指定元素。

1要做什麼

  • 底部入口：沒辦法（或不再）在文章裡高亮的分支，顯示在那一則 AI 回覆的最下方：一條橫線，下面每個入口一行。
  • 重疊降級：新選取跟舊高亮重疊時，舊的降到該則回覆的底部入口，新的變成高亮。範圍完全一樣就直接開舊的。
  • 分支列表：分支面板左上角的圖示變成按鈕，點了用滿版清單列出目前主對話的所有分支，依位置排序；幽靈分支獨立一區在最下面。
  • 連結幽靈分支：有幽靈分支時，選字後多一顆「連結幽靈分支」，選一條，它就變成這段文字的高亮。

2概念一：三種狀態只看兩個欄位

分支錨點有三個相關欄位：anchor_message_id（錨在哪一則回覆）、anchor_start／anchor_end（回覆原始文字裡的字元位置）。三種狀態就是這些欄位「有沒有值」的組合：

狀態anchor_message_idstart／endis_orphaned畫面
inline 高亮有有False文字內高亮
底部入口有空False該則回覆最下方
幽靈空空True分支列表的幽靈區、連結幽靈選單

所以「降級」只是把 start／end 清空，其餘不動。前端現在已經有 precise 旗標（後端回傳 start 與 end 都有值才是 true），precise === false 的分支就是底部入口，不需要新欄位，也不需要 migration。

附帶好處：F7 之前建的分支本來就沒有 offset，現在畫面上找不到它們；照新定義它們會自動出現在各自回覆的底部入口。

3概念二：半開區間的重疊判定

offset 用半開區間 [start, end)：包含 start 那個字，不包含 end 那個字。兩段 [a, b) 與 [c, d) 重疊的條件只有一行：

overlap = a < d and c < b
舊新結果說明
[10, 20)[15, 30)重疊 → 舊的降級部分重疊
[10, 20)[5, 40)重疊 → 舊的降級新的包住舊的
[10, 20)[12, 18)重疊 → 舊的降級舊的包住新的
[10, 20)[20, 30)不重疊相鄰：舊的最後一字是 19，新的從 20 開始
[10, 20)[10, 20)完全相同 → 不新建，開舊的先檢查這個，再檢查重疊

只比對「同一則回覆、有 offset、不是幽靈」的分支。同時重疊兩個舊高亮就兩個都降級。

4概念三：一個交易改兩筆資料（2d 選 A）

建立分支時要「新增一條」並「修改舊的幾條」。放在同一個資料庫交易：最後一次 commit() 才真正寫入，中途任何一步出錯，全部都不生效。

# POST /chats/{root_id}/branches（概念）
same = 找同一則、start/end 完全相同、非幽靈的分支
if same:
    return {..., "reused": True, "demoted_ids": []}      # 不寫入任何東西

demoted = demote_overlaps(session, anchor_id, start, end)  # 只改物件，還沒 commit
session.add(Branch(...))                                   # 新分支
session.commit()                                           # 兩件事一起寫入
return {..., "reused": False, "demoted_ids": demoted}

demote_overlaps 刻意不自己 commit：建立分支和連結幽靈分支（概念四）都用它，各自在最後統一 commit。前端只打一次 API，成功後照舊 loadBranchList 重抓清單，舊高亮自然變成底部入口。

5概念四：重連＝改錨點，並把分支接回新位置

分支的第一則訊息用 parent_id 指向錨點回覆；在分支裡對話時，後端沿著 parent_id 往上收集上下文。G6 幽靈化時把這條線剪斷了（parent_id = NULL）。重連要把線接到新的錨點：

幽靈分支
首則 parent_id = NULL
→
選字 → 選這條幽靈
→
anchor＝新選取
首則 parent_id＝新錨點
→
之後在分支裡對話
上下文來自新位置
# POST /branches/{id}/relink（概念）
if not br.is_orphaned: 409
檢查錨點在這個對話裡（同 create_branch）
if 有完全相同範圍的分支: 409          # 兩條分支不能疊在同一段
demote_overlaps(..., exclude_id=br.id)
br.anchor_message_id, br.anchor_start, br.anchor_end = 新選取

首則訊息.parent_id = 首則訊息.anchor_message_id = 新錨點
session.commit()

6概念五：幽靈清單只列自己的

幽靈分支沒有錨點，也就不知道屬於哪個對話，清單要靠別的方式只列「這個瀏覽器」的（對話清單是用 session_id 過濾的）。

  • attach_root_id 原本設計給「掛在整個對話底部」，現在用不到。改成：幽靈化時記下原本所屬對話的樹根，清單用那則訊息的 session_id 過濾。
  • G6 已經產生的舊幽靈沒有這個值 → 改看分支首則訊息的 session_id。（沒送過訊息又是舊資料的幽靈會找不到，只影響開發資料。）
  • FK 陷阱：attach_root_id 是外鍵且沒有 ON DELETE，直接刪對話會被擋下。刪對話端點在刪訊息前先把指向它們的 attach_root_id 設為 NULL，幽靈分支本身保留。

7概念六：前端三個技巧

7.1 多鍵排序

列表要「依回覆順序 → 同一則內高亮依位置 → 底部入口排在該則高亮之後」。把每項換成一組數字，逐項比較：

const key = (b) => [
  indexOfMessage(b.anchor_message_id),     // 不在目前對話裡 → Infinity，排最後
  b.precise ? 0 : 1,                       // 同一則：高亮在前、入口在後
  b.precise ? b.anchor_start : Date.parse(b.created_at),
];
list.sort((x, y) => {
  const a = key(x), b = key(y);
  for (let i = 0; i < a.length; i++) if (a[i] !== b[i]) return a[i] - b[i];
  return 0;
});

7.2 面板內滿版覆蓋

清單只蓋住分支面板，不蓋整個畫面：面板外框已是定位容器（relative），清單用 absolute inset-0 就會剛好貼齊面板四邊；拖寬面板時清單跟著變寬。整頁彈窗（分支地圖）才用 fixed inset-0。

7.3 捲到指定元素

高亮已經是 <mark data-branch="id">，底部入口加上 data-branch-entry="id"，點列表後：

const el = document.querySelector(
  b.precise ? `[data-branch="${b.id}"]` : `[data-branch-entry="${b.id}"]`);
el?.scrollIntoView({ block: 'center', behavior: 'smooth' });

用 data 屬性而不是 ref：元素分散在每則回覆的 Markdown 裡，集中管理 ref 很麻煩，用選擇器直接找最簡單。
