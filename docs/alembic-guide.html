Alembic 資料庫遷移（Migration）教學

為什麼需要它、它在這個專案做了什麼、以及你之後怎麼用它。

1先搞清楚問題：為什麼需要「遷移」

資料庫的結構（有哪些表、每個表有哪些欄位）不是寫死一次就不再變的。專案長大，你一定會：

  • 加新表（例如接下來要加的 user、session 表）。
  • 給現有表加欄位（這個專案已經加過 title、session_id）。
  • 改欄位型別、加索引、加外鍵。

問題是：這些結構變更，要怎麼「有順序、可重現、可回溯」地套用到資料庫？

這個專案現在的做法有兩個：

  • database.py 裡的 SQLModel.metadata.create_all(engine) —— 只會「建出不存在的表」，不會改已存在的表。
  • migrate.py —— 手寫的一支一支 ALTER TABLE ... 腳本，要自己記得執行、自己記得順序。
migrate.py 的痛點：沒有版本紀錄（不知道哪支跑過）、只能前進不能後退（沒有「退回上一版」）、改錯了要自己手動救。開發機和正式機（Render 上的 PostgreSQL）很容易不同步。

Alembic 就是用來解決這個問題的標準工具。

2Alembic 是什麼

Alembic 是 SQLAlchemy 官方出的「資料庫遷移工具」。你的 sqlmodel 其實就是包在 SQLAlchemy 外面的殼，所以 Alembic 可以直接認得你的 SQLModel 表定義。

它把「每一次結構變更」記錄成一個有編號的版本（revision），像 git 的 commit 一樣：

對應概念GitAlembic
一次變更commitrevision（一個 migration 檔）
往前套用合併分支upgrade
往後退回git revertdowngrade
看歷史git logalembic history
記錄進度commit 指針資料庫裡的 alembic_version 表

Alembic 會在資料庫裡建一張 alembic_version 表，記住「目前套用到哪一版」，所以多台機器／環境永遠知道彼此差幾版。

3三個核心概念

① revision（版本）

一個 revision = 一個 Python 檔，放在 alembic/versions/ 資料夾。檔名像 3a1b2c4d5e6f_add_user_and_session_tables.py，前面那串是版本 id，後面是人讀得懂的描述。每個檔都有 upgrade() 和 downgrade() 兩個函式。

② upgrade / downgrade（前進／後退）

v1
初始表
→
v2
加 user 表
→
v3
加 session 表

upgrade 沿箭頭往前走；downgrade 反方向退回。想退回 v2，就是對 v3 執行 downgrade。

③ autogenerate（自動生成）

你不需要手寫 CREATE TABLE 或 ALTER TABLE。Alembic 會：

models.py
(你想要的結構)
⇄ 比對
資料庫
(目前的結構)
→
產生 migration 檔
(差異部分)

它比對「程式碼裡的 model」和「資料庫實際長相」，自動把差別寫成一個 revision。你只要檢查一下再套用即可。

4在本專案的設定（我接下來會做的事）

要在這個專案引入 Alembic，有三樣東西要建立：

  • alembic.ini —— Alembic 的設定檔（讀連線字串）。
  • alembic/env.py —— 告訴 Alembic「你的表定義在哪裡」，關鍵是這一行：
# alembic/env.py（簡化）
from sqlmodel import SQLModel
from backend import models   # 一定要 import，讓所有 table=True 的 model 都註冊進 metadata
target_metadata = SQLModel.metadata
  • alembic/versions/ —— 存放每個 migration 檔。
關鍵：SQLModel.metadata 會自動收集所有 class Xxx(SQLModel, table=True) 的表。所以 autogenerate 前，一定要先 import 那些 model，否則 Alembic 會以為表不存在、想把它們全部刪掉。

連線字串會沿用 database.py 裡的 DATABASE_URL（從 .env / docker-compose.yml 讀的那個），所以對同一個資料庫操作。

5日常工作流（改結構時的標準動作）

  1. 改 model：在 models.py 新增／修改 table=True 的類別或欄位。
  2. 自動生成 migration： 
    alembic revision --autogenerate -m "add user and session tables"
  3. 檢查產生的檔案：打開 alembic/versions/ 最新那個檔，確認 upgrade() / downgrade() 內容正確（autogenerate 不是萬能，偶爾要手補）。
  4. 套用到資料庫： 
    alembic upgrade head   # 套到最新版
  5. 要退一步： 
    alembic downgrade -1  # 退回上一版
  6. 看目前狀態： 
    alembic current    # 資料庫現在在哪一版
alembic history    # 所有版本清單

6命令速查表

命令作用
alembic init alembic初始化（建立 alembic.ini、env.py、versions/）—— 只做一次
alembic revision --autogenerate -m "描述"依 model 差異自動產生新版本
alembic upgrade head套用所有未套用的版本（到最新）
alembic upgrade <revision>套用到指定版本
alembic downgrade -1退回上一個版本
alembic current顯示資料庫目前版本
alembic history列出所有版本（含父版本鏈）
alembic stamp head直接「標記」到某版而不跑 SQL（用在「表其實已經建好」的情境）

7常見陷阱（SQLModel 特別要注意）

  • 忘了 import model → autogenerate 會產生「刪表」的錯誤 migration。永遠確保 env.py 有 import 所有 model。
  • autogenerate 不是萬能：欄位改名（rename）、改型別、加 server_default、enum 變更等，有時偵測不到或產生錯的 SQL。生成後一定要人工看一遍。
  • downgrade 要自己寫好：autogenerate 的 downgrade() 通常只有「drop table / drop column」，若你的 upgrade 動了資料（例如搬資料），downgrade 要手補對應的還原邏輯。
  • 已套用的 migration 別再改：如果 v2 已經在某台機器跑過，就不要回頭改 v2 的內容，否則那台機器和你本機的歷史會分叉。錯了就「再新增一個 revision 去修正」。
  • 別跟 create_all 混用：引入 Alembic 後，database.py 的 create_db_and_tables() 要停用，否則兩套機制會打架。之後一律用 alembic upgrade head 建表。

8Phase 0 我會實際怎麼用它

Phase 0（安全地基）要加 user 表和 session 表，並把對話綁到使用者身上。實際步驟：

# 1. 安裝
pip install alembic

# 2. 初始化（在 backend/ 下執行）
alembic init alembic

# 3. 改 env.py 指向 SQLModel.metadata（見第 4 節）

# 4. 在 models.py 新增 User、Session 兩個 table=True 類別

# 5. 自動生成第一個 migration
alembic revision --autogenerate -m "add user and session tables"

# 6. 檢查、套用
alembic upgrade head

之後每個 Phase 的結構變更（例如 Phase 1 的 Branch 表、Message 加 branch_id 欄位）都是「改 model → revision --autogenerate → 檢查 → upgrade head」這四步，乾淨且每台環境可重現。

這份教學建立的習慣：從今以後，資料庫結構一律走 Alembic，不再手寫 migrate.py 或 create_all。
