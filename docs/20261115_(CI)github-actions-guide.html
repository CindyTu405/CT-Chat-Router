CI：每次 push 自動跑測試

9 支 harness 現在要記得手動跑。這份教學說明怎麼讓 GitHub 在每次 push 時替你跑，以及為什麼要先修 baseline migration。

1現況與問題

  • 後端有 9 支 harness，前端有 npm run build，但都要人記得跑。忘了跑，壞掉的程式就直接進 main。
  • 臨時資料庫要靠複製本機的 chat_db 才建得出來（pg_dump -s chat_db | psql g2_tmp）。換一台乾淨的機器就沒有東西可以複製。
第二點是 CI 的前提：GitHub 的機器每次都是全新的，上面沒有 chat_db。資料庫必須能從零建出來。

2概念：CI 與 GitHub Actions

CI（持續整合）就是「每次程式有變動，由機器自動檢查一遍」。GitHub Actions 是 GitHub 內建的 CI：你在 repo 放一個設定檔，GitHub 就在事件發生時開一台臨時的 Linux 機器照著做。

名詞意思這個專案
workflow一份設定檔，放在 .github/workflows/ci.yml
trigger（on）什麼事件要啟動任何分支的 push、對 main 的 PR
job一台機器上的一組工作，job 之間互不影響、同時跑backend、frontend
stepjob 裡依序執行的一個指令安裝、migration、跑 harness
service containerjob 旁邊另外開的容器，例如資料庫PostgreSQL（和本機同一個映像檔）

判斷成功或失敗的方式很單純：任何一個 step 的指令結束碼不是 0，整個 job 就是紅色。9 支 harness 失敗時都會以結束碼 1 結束，所以不用改 harness 的判斷邏輯。

紅色不會自動擋下合併。要擋，得另外在 GitHub 設定 branch protection。第一版先不設，只讓你在 commit 旁邊看到綠勾或紅叉。

3概念：migration 要能從零重建資料庫

Alembic 的 migration 是一條鏈：從第一支（baseline）依序執行到最新一支，就該得到目前的資料庫結構。

這個專案的 baseline 是空的。導入 Alembic 時 message、freemodelscache 兩張表已經存在（當時由 create_all 建立），所以 baseline 只是標記「從這裡開始」，沒有寫建表。結果第二支之後的 migration 一遇到 message 就失敗：

$ createdb ci_tmp
$ POSTGRES_DB=ci_tmp uv run alembic upgrade head
# 建 branch 表時要參照 message(id)，但 message 不存在
sqlalchemy.exc.ProgrammingError: relation "message" does not exist

影響不只 CI：哪天要在新機器重建環境（搬主機、災難復原、新的開發機），也只能靠舊資料庫的備份。

4修法一：baseline 補上建表

在 baseline 補上那兩張表「導入 Alembic 當時」的樣子，並且只在表不存在時才建：

# 示意，實際程式由 implementer 撰寫
def upgrade():
    existing = 目前資料庫裡的表名
    if 'message' not in existing:
        op.create_table('message', ...)          # 2026-10-20 當時的欄位，含 session_id
    if 'freemodelscache' not in existing:
        op.create_table('freemodelscache', ...)
疑問回答
會不會動到正式站或本機的 chat_db？不會。它們早就記錄「baseline 已執行」，Alembic 不會重跑已執行的 migration。
為什麼要寫「當時」的欄位，不是現在的？後面的 migration 會再加欄位、刪 session_id。baseline 寫成現在的樣子，後面就會重複加欄位而失敗。
為什麼還要判斷表存不存在？保險。萬一有資料庫是用 create_all 建好、還沒 stamp 就執行 upgrade，不會因為表已存在而失敗。
改已經執行過的 migration 可以嗎？一般不該改。這裡可以，是因為它對已執行過的資料庫完全沒有作用，只影響「從零開始」這條以前走不通的路。
已試做確認：在空資料庫 alembic upgrade head 跑到最新版，pg_dump -s 與 chat_db 比對完全相同（freemodelscache.id 要加 autoincrement=False，否則會多一個 sequence），quota_harness 在上面 ALL PASS。試做的修改已還原，沒有 commit。

5修法二：一支腳本跑完 9 支 harness

新增 backend/dev/run_harnesses.sh，依序跑 9 支，每支印一行 PASS 或 FAIL，有任何一支失敗就以結束碼 1 結束。本機和 CI 都呼叫同一支，兩邊跑的東西才不會慢慢走樣。

# 本機用法（示意）
cd backend && POSTGRES_DB=g2_tmp ./dev/run_harnesses.sh
PASS auth
PASS quota
...
PASS openrouter_connect
9 passed, 0 failed

資料庫名稱固定用 g2_tmp：openrouter_connect_harness 只肯在這個名稱上執行，guest_harness 拒絕 chat_db。這兩道防呆保留不動。

6修法三：workflow 設定檔

# .github/workflows/ci.yml（示意，實際檔案由 implementer 撰寫）
on:
  push:                       # 任何分支
  pull_request:
    branches: [main]

jobs:
  backend:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: pgvector/pgvector:pg16      # 和 docker-compose 同一個映像檔
        env: { POSTGRES_USER: ci, POSTGRES_PASSWORD: ci, POSTGRES_DB: g2_tmp }
        ports: ["5432:5432"]
        options: 等資料庫 healthy 才開始
    env:
      DATABASE_URL: postgresql://ci:ci@localhost:5432/g2_tmp
    steps:
      - checkout
      - 安裝 uv，uv sync --frozen
      - uv run alembic upgrade head        # 順便驗證 migration 鏈能從零跑完
      - ./dev/run_harnesses.sh

  frontend:
    runs-on: ubuntu-latest
    steps:
      - checkout
      - 安裝 Node 20（和 frontend/Dockerfile 一致）
      - npm ci
      - npm run build
  • 沒有任何真的金鑰。harness 用假模型、假登入，CI 裡的資料庫帳密 ci/ci 只存在那台臨時機器上，跑完就銷毀。不需要在 GitHub 設定 secrets。
  • 不會花模型的錢。harness 從來不呼叫真的 Gemini 或 OpenRouter。
  • 時間：本機 9 支合計約 1.5 分鐘，加上安裝，預估每次 3 分鐘內。
還沒驗證的一點：本機跑 harness 時會讀到 repo 根目錄的 .env，CI 上沒有這個檔。可能有模組在缺少某些環境變數（例如 OAuth 的 client id）時行為不同。第一次 CI 執行會告訴我們；若失敗，在 workflow 補上假的值即可，不動程式。

7怎麼驗收

  • 空資料庫 alembic upgrade head 成功，alembic current 印出 a7b8c9d0e1f2 (head)。
  • 該資料庫的 pg_dump -s 與 chat_db 比對沒有差異。
  • chat_db 的 alembic current 不變，資料表不變。
  • ./dev/run_harnesses.sh 印出 9 行 PASS，結束碼 0。
  • push 之後，GitHub 的 Actions 頁面上 backend、frontend 兩個 job 都是綠勾。
  • 故意弄壞一支 harness 的斷言再 push 到測試分支 → backend 變紅；還原後變綠。

完整的可執行指令在 PLAN_v2.md「CI 規格與驗收」。
