重傳最後一則回覆

原地重新生成、幽靈分支的資料欄位、409 防呆、緩衝清除的競態、前端把串流寫回同一則訊息。

1要做成什麼樣子

  • 主對話與分支的最後一則 AI 回覆，功能列在「複製」右邊多一顆重傳鈕（lucide RefreshCw），成功或失敗都有。
  • 按下 → 用選單目前選的模型重新生成，取代舊回覆。
  • 舊回覆上開過的分支 → 變成幽靈分支（資料保留，暫時不顯示；之後做幽靈分支 UI 再出現）。
  • 前端「⚠️ 連線錯誤」那種沒有訊息 id 的回覆，不顯示重傳鈕。
  • 不做 DESIGN_P3 主題 3（刪除舊一輪的交易）；改用「原地更新」。

2概念一：原地重新生成，而不是刪掉重建

刪掉舊回覆、建一則新的原地更新（採用）
訊息 id變新的不變
外鍵分支的錨點、子訊息都指向舊 id，要先處理才能刪沒有東西被刪，不用排順序
切走再切回（Bug A 續讀）前端要換成新 id沿用同一個 id 的緩衝，原本的續讀直接可用
原子性刪＋建要包在同一交易一次 UPDATE＋分支幽靈化，一個 commit

3概念二：幽靈分支的資料欄位（DESIGN_P3 主題 2）

分支錨在一段 AI 文字上（anchor_message_id＋anchor_start/end）。文字重新生成後，那段位置就沒有意義了。主題 2 定的三種狀態：

狀態anchor_message_idattach_root_idis_orphaned
inline 錨定（現在全部都是）有空false
底部入口（重連後，之後做）空有false
幽靈空空true

migration

alter branch.anchor_message_id drop not null
add   branch.is_orphaned    boolean not null default false
add   branch.attach_root_id uuid null  (FK message.id)

幽靈化要做三件事

  1. 分支：anchor_message_id = NULL、anchor_start/end = NULL、is_orphaned = true。anchor_text 保留，之後幽靈清單可以顯示「原本選的是哪段字」。
  2. 分支的第一則訊息（root_message_id）：parent_id = NULL、anchor_message_id = NULL。
    原因：分支第一則訊息的 parent 就是那則 AI 回覆。不斷開的話，樹狀圖和「刪除整串對話」還是會把幽靈分支算進這棵樹。
  3. /chats/roots（側邊欄列表）只列 branch_id IS NULL 的根。
    原因：斷開後，分支第一則訊息自己變成「沒有 parent 的訊息」，不加這個條件就會被側邊欄當成一個新對話。
部署：這次有 migration。虛擬機 git pull 後要 sudo docker compose up -d --build，再 sudo docker compose exec api alembic upgrade head（CLAUDE.md Production deploy）。

4概念三：用 409 擋掉不該發生的重傳

情況回應原因
id 不存在或不是 AI 訊息404
模型不在白名單403跟 /chat 同一個檢查，要在改資料之前
這則還在生成中409兩個 task 同時寫同一則會互相覆蓋
不是同一條線的最後一則（後面還有同 branch_id 的子訊息）409只允許最後一則；中間那則重新生成會讓後面的對話失去前提

「同一條線」：主對話看 branch_id IS NULL，分支看同一個 branch_id。錨在這則回覆上的分支，其訊息也是它的子訊息，但 branch_id 不同，不算「後面還有對話」，而是要被幽靈化的對象。

409 Conflict 的意思是「請求本身沒錯，但跟伺服器目前的狀態衝突」。前端照理不會送出這種請求（按鈕只在最後一則、生成中不顯示），這是給雙擊、兩個分頁同時按這類情況的保險。

5概念四：緩衝清除的競態（race condition）

Bug A 的設計：生成完成後，緩衝 GENERATIONS[id] 保留 60 秒，讓正在續讀的前端讀到結尾，然後清掉：

# run_generation 的 finally（現況）
await asyncio.sleep(60)
GENERATIONS.pop(ai_msg_id, None)      # ← 不管現在裡面是誰，直接清

以前每則 AI 只生成一次，沒問題。有了重傳，同一個 id 會生成第二次：

第 1 次生成完成
開始等 60 秒
→
第 20 秒按重傳
放入「新」緩衝
→
第 60 秒舊 task 醒來
把「新」緩衝清掉
→
切走再切回
讀不到生成中的內容

修法：只清「自己放進去的那一份」。

await asyncio.sleep(BUFFER_RETENTION_SECONDS)
if GENERATIONS.get(ai_msg_id) is buf:    # is：同一個物件才清
    GENERATIONS.pop(ai_msg_id, None)

60 秒改成模組常數 BUFFER_RETENTION_SECONDS，測試時可以調短。

6概念五：前端把串流寫回「同一則」訊息

按鈕何時出現

MessageList 新增 onRetry prop（主對話、分支各自傳）。重傳鈕只在以下條件都成立時出現：

  • 是列表中的最後一則，而且是 AI
  • 有 id（排除「⚠️ 連線錯誤」）
  • 不在 loading 中
  • 有傳 onRetry

G8 的 buildMessageActions 加第二個參數，有 onRetry 才加入重傳項目，排在複製右邊：

const buildMessageActions = (msg, { onRetry } = {}) => [
  { id: 'copy',  label: '複製',     icon: Copy,      run: () => copyText(msg.content) },
  ...(onRetry ? [{ id: 'retry', label: '重新生成', icon: RefreshCw, run: () => { onRetry(msg); return false; } }] : []),
];

run 回傳 false：重傳不需要「✓」回饋，畫面會直接變成 Thinking...。

寫回同一則

跟送出訊息的流程幾乎一樣，差別是不新增訊息，而是把最後一則的內容清空、換上新模型名稱，再把串流文字寫進同一個 id：

setMessages(prev => prev.map(m => m.id === msg.id ? { ...m, content: '', model_used: model } : m));
const res = await fetch(`${API_URL}/messages/${msg.id}/regenerate`, { method: 'POST', body: { model } });
// 之後用跟 handleSend 相同的 reader 迴圈，比對 id 寫入

切走再切回：loadChat 看到最後一則 AI 還在生成，就呼叫既有的 resumeGeneration。id 沒變，這段不用改。

重傳後

  • 主對話：重新抓分支清單（loadBranchList），被幽靈化的分支高亮就會消失。
  • 右側面板如果開著被幽靈化的分支 tab，就關掉。後端在 header X-Orphaned-Branch-Ids 回傳被幽靈化的分支 id（逗號分隔）。
